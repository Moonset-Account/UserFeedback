# gptrepair — GPT 分区表修复与重定位

为虚拟块盘实现的防御性 GPT（UEFI 2.10, §5.3）修复/重定位库。输入一个带整扇区
读写接口的镜像、逻辑扇区大小和目标容量变更计划，在**有一致可信来源且所有分区
都能原样容纳**的前提下，重建主、副两份 GPT，保持磁盘 GUID、分区项数组和用户
数据区字节不变。

模块名：`gptrepair`，无第三方依赖，仅使用 Go 1.20 标准库。

## 公开 API

### 后端接口

| 符号 | 说明 |
| --- | --- |
| `SectorDisk` | 块设备最小契约：`SectorSize()`、`TotalSectors()`、`ReadSectors(lba, count, dst)`、`WriteSectors(lba, src)`，只接受整扇区、做范围检查 |
| `ResizableDisk` | 可选能力：`ResizeSectors(n)`。扩盘只追加零扇区，缩容只截断尾部，绝不移动用户字节 |
| `MemoryDisk` | 内存后端（测试/合成镜像），`NewMemoryDisk(sectors, blockSize, resizable)`，支持 `Clone()` |
| `FileDisk` | 普通文件后端，`OpenFileDisk(path, blockSize, totalSectors)` / `Close()`，写入后 `fsync`，支持 `ResizeSectors` |

### 修复入口

| 符号 | 说明 |
| --- | --- |
| `Plan{TargetSectors}` | 目标容量（扇区）。`0` 表示保持当前容量 |
| `Repair(d, plan) (*Report, error)` | 校验并修复/重定位，返回写扇区数、扩缩容标记、清理的陈旧副本等 |
| `Inspect(d) (*Inspection, error)` | 纯只读校验，返回所有候选副本、可信副本和逐条失配原因，不写盘 |
| `Header` | 解码后的 92 字节 GPT 表头结构 |
| `DefaultEntrySize=128`、`DefaultEntryCount=128` | 默认分区项几何（重建时实际几何沿用可信来源，不重新格式化） |

### 错误哨兵（`errors.Is` 判定）

| 错误 | 触发条件 |
| --- | --- |
| `ErrNoTrustworthySource` | 不存在任何一份表头 CRC、分区项 CRC、边界、自洽结构全部通过的完整副本 |
| `ErrArbitrationRequired` | 两份各自校验通过的副本在磁盘 GUID 或分区项内容上矛盾，需人工裁决；此时**不执行任何写操作** |
| `ErrPartitionOverflow` | 缩容目标无法原样容纳某个分区（分区首/末 LBA 越过新可用区） |
| `ErrGeometry` | 目标容量小到无法容纳 GPT 元数据，或分区项数组不满足扇区对齐 |
| `ErrArgument` | 空盘、非法扇区大小、非整扇区读写、后端不支持容量变更等 |

## 可信判定规则（全部满足才采信一份副本）

1. 签名 `EFI PART`、revision 1.0、HeaderSize 不超过扇区大小；
2. 表头 CRC：对 HeaderSize 字节、CRC 字段清零后计算 IEEE CRC32；
3. 分区项数组 CRC（对数组全部字节计算 IEEE CRC32）；
4. 边界：表头与分区项数组均在盘内且互不重叠，可用区非空且不越过盘末；
5. 结构自洽：主表位于 LBA 1、分区项从 LBA 2 开始；副表回指 LBA 1 且其分区项
   数组紧邻副表头之前；
6. 相互引用：对端也存在且自洽时，两表必须互相指向、共享同一可用区与分区项
   几何（各自保留自己的分区项 LBA）；对端缺失时单份完整副本仍可采信；
7. 每个非空分区项的首/末 LBA 必须落在该表头声明的可用区内。

**禁止拼接**：主表头损坏但分区项完好、副表头完好但分区项损坏这类“两份各自
残缺”的情况不会被合并，直接返回 `ErrNoTrustworthySource`。指针只从已通过完整
校验的表头跟随，损坏表头无法把扫描重定向到攻击者指定的 LBA。

## 迁移与崩溃安全

迁移期间可寻址范围取 `max(旧容量, 目标容量)`：

- **扩盘**：先把后端扩到目标容量（旧字节不动，新尾部为零），再写元数据；旧副
  本可能仍留在原末尾，新副表落盘后才清理它。
- **缩容**：先在迁移地址空间内把新主、副表写到目标布局，**两份都写完并复验通
  过后才执行截断**；若某分区越过新末尾，在任何写操作之前就返回
  `ErrPartitionOverflow`。

写入顺序（每个 `WriteSectors` 都是整扇区、可能成为停机点）：

1. 新副表分区项 → 2. 新副表头；
2. 清理陈旧副本：先清零其分区项、再清零其表头（半成品不会伪装成有效表）；
3. 新主表分区项 → 4. 新主表头（表头最后写，避免指向半写数组）；
4. 缩容截断；
5. 保护性 MBR（LBA 0，最后写，不参与 GPT 副本的崩溃窗口）；
6. 以“重新开盘”的视角对结果再跑一遍完整校验。

因此在任意一次整扇区写之后停机，盘上至少保留一份完整的旧表或新表；重开后
`Repair` 重新探测即可继续并收敛，绝不会以两份残缺内容为依据。

## 验证范围（本地合成数据，无联网、无真实设备、无外部依赖）

所有镜像均由测试在内存中按 UEFI 布局合成，断言基于实际 `go test` 执行：

- 健康盘 `Repair` 为零写空操作、字节逐字节不变、可重复运行收敛；
- 主表损坏从副表重建、副表损坏从主表重建，磁盘 GUID 与分区项字节保持；
- 两份副本各自有效但磁盘 GUID/分区项矛盾 → `ErrArbitrationRequired` 且零写；
- 两份各残缺（表头 CRC 与分区项 CRC 分别损坏）→ `ErrNoTrustworthySource`，不拼接；
- 分区项 CRC 失配、交叉引用损坏、分区越可用区边界、坏签名/零扇区等校验分支；
- 扩盘：用户标记字节与 GUID 不变，原末尾陈旧副本被清除；
- 缩容：分区可容纳时成功并最后截断；分区越过新末尾时拒绝且磁盘原样不动；
- 目标容量不足以容纳元数据 → `ErrGeometry`；
- 512 与 4096 字节两种逻辑扇区；
- **崩溃注入**：对同容、扩盘、缩容三条路径，先测量一次完整运行的扇区写总数，
  再在每个扇区写计数点注入停机，断言 (a) 停机后 `Inspect` 至少发现一份可信
  副本，(b) 续跑收敛到目标容量且双副本复验通过、用户字节不变；
- 手工构造的“扩盘中途（新副表已写、旧副本仍在）”和“缩容中途（双新表已写、
  尚未截断）”交错状态，验证重开续跑；
- `FileDisk` 真机文件路径：停机、关闭、按当前文件大小重开、续跑、再复验；
- 后端不支持 `ResizeSectors` 时容量变更被拒，同容修复仍可用；
- 扇区读写越界、非整扇区写、零长度扩容等参数检查。

## 已知边界（如实记录）

- 仅实现 GPT revision 1.0、分区项大小为 128 的整数倍且数组按扇区对齐的布局；
  其它 revision 在探测阶段被拒绝。
- `FileDisk` 需要调用方按虚拟盘当前容量传入 `totalSectors` 重开（容量由虚拟块
  盘层登记，本库不自行扫描文件大小推断几何）。
- 保护性 MBR 的 0xEE 分区大小受 32 位字段限制，超过 2^32-1 扇区的盘按 UEFI
  惯例填 `0xFFFFFFFF`。
- 修复只重建元数据；分区自身文件系统内容不在处理范围内，也不会被改动。
