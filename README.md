# 邮件加密网关：投递包编排

为至多 **12 名收件人** 计算满足全部安全约束的拆投方案，优化目标按字典序为：

1. **包数最少**；
2. 包数相同时 **封套数最少**；
3. 成本再相同时给出确定的、可复现的平局结果（与输入顺序无关）。

本项目只实现题面规定的**防御性安全判断**：不包含、也不会生成任何利用、入侵、攻击或规避载荷；全部数据均为本地合成数据，无网络访问、无外部依赖，标准库即可运行。

## 安全模型（输入与约束）

### 输入模型

- `Key(key_id, suite, holders, identity, resolvers)`
  - `holders`：该密钥的**全部持有人**，包括不在收件人列表里的组外人员。
    任何持有人都能用它解封套，因此组外持钥人会直接影响安全性。
  - `identity`：包头标识反查到的身份；可以是匿名标识。
  - `resolvers`：输入明确给出的、能把该标识反查到身份的人。
- `Recipient(recipient_id, suites, can_see, decrypt_scope)`
  - `suites`：支持的加密套件。
  - `can_see`：允许其知道身份的同信收件人（密送可见性名单）。
  - `decrypt_scope`：允许其解密正文时，封套密钥持有人必须落在其中的范围。

### 一个包合法的四个必要条件（`evaluate_package`）

1. **套件一致**：存在一种所有成员都支持的套件；一次封包只选一种，
   取共同套件中字典序最小者。
2. **包头可见性（密送）**：对每把选中的密钥，凡在包内且能反查其身份的人
   （`resolvers ∩ 成员`），都必须在该身份主人的 `can_see` 名单内。
   - 身份对“不在 `resolvers` 里的人”天然不可见——这正是“密送身份只能
     对部分人隐藏”的建模。
   - 身份不在收件人表中（匿名标识）且存在可反查者时，没有允许名单可依，
     该密钥按违规拒绝。
3. **解密范围（组外持钥人）**：每把选中密钥的**全部持有人**（含组外）都必须
   落在包内**每名**收件人的 `decrypt_scope` 内。组外未授权持钥人能打开的包
   直接排除，并在 `violations` 中点名违规持有人与被违反的收件人。
4. **人人可解封**：选中的封套密钥要覆盖全部成员，每名成员至少持有其中一把
   有效密钥。封套选择本身是一个最小集合覆盖问题，用位掩码 DP 求最少封套，
   平局取 `key_id` 字典序最小的方案。

### 顶层规划（`plan_delivery`）

- 先评估全部 `2^n − 1` 个收件人子集的成包可行性与最少封套数；
- 再对“恰好覆盖全员”的集合划分做有序子集 DP，固定最低位成员属于最后一个包，
  每个划分恰好枚举一次；
- 成本为 `(包数, 封套数)`，划分签名仅用于成本完全相同时的确定性平局；
- 输出前按成员 id 元组对包排序，保证输出顺序与输入/枚举顺序无关；
- 不存在任何安全拆投时抛出 `InfeasibleDeliveryError`，信息中区分
  “存在无法独立成包的收件人”与“单包均可行但合包组合失败”。
- 收件人数超过 12 抛 `ValueError`；空输入返回空方案。

## 公开 API

```python
from mail_gateway import (
    Key, Recipient,                 # 输入模型
    PackageOption,                  # 单子集评估结果（含 violations）
    PlannedPackage, DeliveryPlan,   # 方案模型（package_count/envelope_count）
    evaluate_package,               # 评估一个子集能否成包
    plan_delivery,                  # 求最优安全拆投
    InfeasibleDeliveryError,        # 无安全拆投
    MAX_RECIPIENTS,                 # = 12
)
```

`DeliveryPlan` 提供：

- `package_count` / `envelope_count`：两级优化目标值；
- `packages`：`PlannedPackage` 元组，每个包含 `members`、`suite`、
  `envelope_key_ids`；
- `recipient_to_package()`：收件人到所在包的映射。

## 验证范围（均基于实际执行与断言）

当前 22 个测试全部通过（标准模式与 `python3 -I` 隔离模式各实跑一次）。

1. **密送部分隐藏（`test_bcc_visibility.py`，5 例）**
   - 同一组钥在不同包中：包内无人能反查时身份成功隐藏；第三人能反查且在
     允许名单内时同钥仍可安全使用；
   - 能反查但不在允许名单 → 密钥被拒绝并给出违规原因；
   - 匿名标识有人可反查 → 拒绝；无人可反查 → 放行；
   - 端到端规划中泄露钥被排除，改用安全钥完成投递。
2. **组密钥与组外持钥人（`test_group_key.py`，5 例）**
   - 两人共用组钥、第三人也持钥、组外 `mallory` 同样持钥：未授权时组钥在
     任意包（含单人包）都被拒绝，违规信息点名 `mallory`；
   - 有个人钥兜底时规划结果不使用任何 `mallory` 能打开的封套；
   - 所有人范围均覆盖 `mallory` 时一把组钥封套覆盖全员；
   - `mallory` 作为收件人但某成员未授权她 → 强制拆包；
   - 唯一密钥泄露且无人授权 → `InfeasibleDeliveryError`。
3. **优化正确性（`test_optimization.py`，4 例）**
   - n = 1..5、每个 n 各 10 个固定随机种子的合成实例，共 50 个实例与
     **独立暴力枚举**（穷举全部集合划分）逐一对账 `(包数, 封套数)`，
     并对每个可行方案做独立不变量复核；
   - 组钥共享使 3 人方案从 3 封套降为 1 封套；
   - 封套选择与划分选择的两级确定性平局，且与输入顺序无关。
4. **边界与交错（`test_boundary_and_edge.py`，8 例）**
   - 空输入返回空方案；13 人抛 `ValueError`；
   - 12 人共享组钥 → 1 包 1 封套；12 人套件两两不相交 → 12 包 12 封套；
   - 3 个不同种子的 12 人随机实例独立不变量复核；
   - 无共同套件强制拆包；套件、密送可见性、解密范围三类约束同时生效的
     手工交错场景，验证最优解为 2 包 2 封套且违规钥绝不入选。

独立不变量复核（`tests/helpers.py: assert_plan_invariants`）不依赖规划器
结论，直接从输入重新验证：每人恰好入一包、每包套件全员支持且全包包内一致、
每人至少能解一个封套、可见性约束、以及“所有封套持有人 ⊆ 每名成员解密范围”。

### 实测性能

12 人最坏情况（4095 个子集全部评估、无任何合包可行）实测约 **0.05 秒**
（Python 3.11.6，darwin），测试中以 5 秒为断言上限。

## 已知边界与取舍

- 可见性以输入显式给出的 `resolvers` 为准：无法反查标识的人看不到对应身份，
  这是题面“密送身份只能对部分人隐藏”的直接建模。
- 解密范围按**包级**保守判定：任一封套的组外持有人不在某成员的授权范围内，
  该密钥就不得出现在该成员所在包中，而不是允许成员只靠自己的封套“忽略”
  其他封套——因为同包所有封套都在可获取的投递材料内。
- 平局规则（字典序）是确定性需要，不属于题面优化目标；改变它不影响
  `(包数, 封套数)` 的最优性。
