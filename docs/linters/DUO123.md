# DUO123

This linter looks for unsafe use of the Python `requests` library.

This library has become the de facto standard for making HTTP requests. This
linter specifically searches for situations where HTTPS requests are made with
SSL certificate verification turned off via the `verify=False` keyword argument.

## Problematic code

```python
import requests

request = requests.get("https://google.com", verify=False)
```

## Correct code

```python
import requests

request = requests.get("https://google.com")
```

## Local assignment analysis

The default detection only recognizes a literal `verify=False` keyword. An
optional intra-procedural analysis can additionally track the value of the
`verify` keyword when it comes from a local variable. It is enabled by
constructing the linter with `intraproc_analysis=True` (the flake8 default
path keeps the historical behavior unchanged):

```python
linter = BadRequestsUseLinter(intraproc_analysis=True)
```

The analysis understands boolean constants, variable copies, sequential
reassignment, statically decidable `if`/`else` branches, early `return` and
loops (whose state converges over a finite fixed point). Each call is
classified using the value reachable on the live path at the call site:

* **Confirmed (DUO123)** — every supported path reaching the call proves
  `verify` is `False`. The message keeps the real call location and appends
  the assignment line(s) that produced the value.
* **Needs review** — true and false paths merge, the value comes from an
  unknown call, or the construct is unsupported. A distinct
  `DUO123 unable to determine "verify" value ... manual review required`
  result is emitted; an unknown value is never reported as confirmed safe.
* **No result** — every supported path proves `verify` is `True`, the keyword
  is absent (requests then verifies by default), or the call is unreachable.

Only calls statically bound to the imported `requests` module are analyzed. A
same-named local object, e.g. `requests = MyClient()`, is not treated as the
library. Function parameters, local rebindings and nested function/class
scopes keep their values isolated from one another.

## Rationale

HTTPS certificate verification ensures your requests are communicating with
whom they're supposed to be. Without this there could be an attacker
impersonating the server you intend to be communicating with. To prevent this
you must ensure certification verification is enabled.

## Exceptions

* Code connecting to internal network services (although these should strive for full HTTPS as well)
* Code connecting to local development services or in test environments
